# 数据模型与一致性

状态：逻辑模型设计；物理字段类型和迁移脚本在实施时生成。主键默认不可预测 UUID，时间使用 UTC 存储并在界面按 Asia/Shanghai 展示；整数点数和人民币最小货币单位分开存储。

## 一、账号、身份与权限

`users`：用户 ID、昵称、头像资源、账号状态、创建时间和注销状态。昵称不唯一且不作为关系键。

`phone_bindings`：用户 ID、手机号加密值、用于唯一性查询的受保护索引、验证时间、绑定状态和历史。一个有效手机号只关联一个有效账号；换绑和号码回收处置不能抹去审计记录。

`sessions`、`guest_sessions`：会话摘要、用户或游客归属、设备标识、到期和撤销时间。用户凭据不明文落日志。游客只保存必要匿名信息，不与实名验证资料混用。

`test_access_grants`、`test_access_sessions`：环境、世代、邀请摘要、到期、兑换次数上限、允许范围、撤销状态及获准会话。与站内账号及房间成员分开建模，测试准入不自动赋予创作权限。

`identity_checks`：用户、核验提供方引用、结果状态、成年状态、有效期和最小必要证据。产品调整尚待确认时不启用虚假的“已成年”默认值；优先保存核验结果和外部引用而非完整身份证影像。

`role_assignments`、`account_restrictions`：角色及按能力生效的限制，包含范围、原因、生效/结束时间、操作者和解除记录。角色赋权与业务账号状态分别判断。

## 二、游戏与不可变版本

`games`：作者 ID、目录状态、当前部署范围、当前发布 ID、平台限制、归档和软删除时间。发布指针按部署范围区分，禁止引用其他范围版本授权；作者归属变更首发不提供自助功能。

`game_versions`：游戏 ID、版本序号、来源（上传/AI/官方迁移）、起始版本、清单摘要、源码摘要、产物摘要、审核状态和协议版本。`(game_id, version_number)` 唯一；送审后文件与元数据冻结。

`assets`、`version_assets`：存储键、内容摘要、大小、类型、扫描状态、所属版本、访问等级及保留状态。关联公开版本、任务、订单证据或进行中对局的文件不能被普通草稿清理删除。

`review_submissions`、`review_events`：快照版本、提交人、发布选项、处理人、状态、结论与原因；一个游戏只能有一个有效待审核版本，通过数据库部分唯一约束或等效事务机制保证。

`publication_eligibilities`：游戏、适用发布范围、核查状态、证据引用、有效期、撤销原因及核查责任人。状态为待核实、有效、失效或撤销。平台审核批准与此对象独立；是否需要何种外部证据见文档 16，不把“暂不清楚”当作有效。

`releases`：游戏、版本、环境、范围、发布动作、操作者、前一发布、原因及生效时间。范围只能由可信服务端确定；指针变更、审计与 outbox 同事务提交。

## 三、AI 工程与任务

`projects`：作者、游戏、当前工作基线、`workspace_revision`、当前草稿快照、可编辑性及最后同步时间；工作基线不等于目录生效版本。基线切换和草稿保存使用比较交换，不能无条件覆盖。

`draft_snapshots`：工程、快照摘要、父修订、需求文本、元数据、源码引用、创建原因及时间。快照内容不可变，工程指针可更新；AI 完成新增候选版本，不自动切换已被作者更新的工作区。

`ai_quotes`：需求快照、基线版本、价格、规则版本、可交付范围、有效期和确认状态。失效报价不可直接执行。

`ai_tasks`：用户、报价、基线版本、输出版本、任务状态、执行标识、租约、超时时间、失败类型和结算引用。用户提交幂等键非空，按用户与操作域唯一。

`ai_attempts`：任务、尝试序号、提供方、用量、成本记录、运行检查结果和脱敏错误。平台重试增加尝试记录而不是新增用户收费任务。

`provider_budget_accounts`、`provider_cost_reservations`：环境/供应商预算周期、上限、已确认成本、保守预留、调用引用及结算状态。所有真实调用共用成本边界，不能因免费任务而跳过；超时仍可能发生供应商费用，预留须经核实结算。

`quality_cases`：原任务、用户描述、需求与产物证据、核实结论、免费修复任务、补偿流水和处理时间。任务质量问题不能直接改写原成功状态掩盖交付历史。

## 四、账本与支付

`point_accounts`：用户、可用余额、冻结余额和并发控制版本，余额均不得为负。

`point_lots`：用户、来源、来源订单或活动、初始数量、可用/冻结/已消费/已失效数量及到期时间。补偿记录能追溯原消费，不能将原赠送点数重新标成付费。

`point_transactions` 与 `point_entries`：业务动作、唯一业务键、关联任务或订单、原因、数量和账户分区的增减分录。冻结是可用转冻结，结算是冻结转已消费，释放是冻结转可用；充值与到期有明确来源/去向。

`point_allocations`：任务冻结从哪些批次取得多少点数，以及后续结算和补偿分配。批次汇总与账户汇总必须一致。

`payment_orders`：用户、渠道、金额分、币种、购买点数、商品规则快照、订单状态和到期时间。商品价格变更不改变历史订单。

`payment_transactions`：平台订单、渠道、渠道交易号、金额及当前已核实状态。渠道与渠道交易号组成唯一交易映射；同一交易可以具有多次状态通知。

`payment_events`：渠道事件 ID 或稳定语义事件键、交易引用、事件类型、校验结果和脱敏载荷摘要。按事件身份去重，不把交易号单独作为事件唯一键，避免阻挡同一交易的后续状态变化。

`payment_notification_receipts`：每次渠道通知的接收时间、请求关联 ID、验签结果及所关联事件；重复投递可各自留痕，但不能重复推进财务动作。退款引用独立渠道退款号，入账仍由唯一业务入账键兜底。

`refund_orders`：原支付订单、退款金额、点数处理方案、冻结权益、渠道退款号、状态、理由和复核人；累计退款不得超过实际支付可退金额，退款中金额也计入占用。

`reconciliation_cases`：对账日期、差异类型、两端证据和处理结果。支付重复通知可以多条审计记录，但只能对应一次有效入账。

## 五、运行与社区

`play_sessions`：环境、世代、发布或预览范围、测试访问会话引用、玩家身份、游戏、版本、启动状态、授权到期、最后心跳及关闭原因。

`game_saves`：用户、游戏、`save_schema_version`、JSON 数据、数据大小、生成游戏版本、revision 及更新时间；三者组合唯一。通过当前运行会话限定归属，客户端不能指定别人的账号。游客本地档不自动写入此表。

`rooms`、`room_members`：环境、世代、发布范围、房间标识、固定版本、主持服务实例、租约、状态、玩家席位和重连期限。玩家 ID 不直接公开绑定手机号；跨测试范围的邀请和重连必须拒绝。

`room_events`、`room_snapshots`：动作唯一 ID、序号、快照摘要、规则版本和持久化位置；私有状态存储加密且不进入公共分析日志。`(room_id, action_id)` 唯一；提交时锁定或条件更新房间记录，校验租约隔离令牌和预期序号，原子更新状态引用、事件与动作结果，确认消息在提交后发送。

`comments`：游戏、作者、根评论、内容、公开状态及删除状态；服务端校验回复深度。`likes`、`favorites` 的用户与游戏组合唯一。

`reports`、`appeals`：对象类别与 ID、提交人、原因、证据、处理状态及结果；处理人访问有审计。

`test_feedback`、`test_feedback_events`：环境、测试会话或用户、游戏及版本、可选房间/任务、设备类别、问题描述、经选择的诊断摘要、附件引用、等级、处理人、状态、修复版本与复测结果。默认仅提交者、相关作者和受权处理人员可看；作者不能查看同反馈附带的其他用户隐私。

`notifications`：接收人、事件唯一键、类别、关联对象、已读状态；相同业务事件不重复生成多条同类消息。

## 六、公共基础数据

`outbox_events`：在业务事务中创建，含事件 ID、聚合对象、序号、载荷、投递状态及重试记录。消费者写 `processed_events` 或业务唯一键，不假设队列绝不重复。

`audit_events`：操作者、动作、对象、脱敏前后值、请求关联 ID、理由及时间。后台不得提供普通删除审计接口。

`config_versions`：键、作用域、版本、值、操作人及生效时间；价格、配额、限流、任务时限采用可追溯配置，不由前端随意传入。

`artifact_jobs`：环境及世代、归属主体（账号或测试会话）、用途、类型（扫描/检查/导出/回收）、输入摘要、状态、执行租约、阶段进度、结果引用、脱敏错误和到期时间。访客主体只用于反馈附件等明确授权的操作，不可创建游戏工程导出；状态为排队、运行、成功、失败、已过期，不编造无法测量的百分比。

`artifact_retention_holds`、`cleanup_jobs`：资源受保护的原因、引用对象、保留到期或解除条件、清理提议、执行及恢复结果。删除前重新检查有效引用，不依赖创建清理任务时的一次性判断。

## 七、事务及迁移约束

固定账户、订单与批次锁定顺序，冲突时使用有界重试。点数操作、订单状态变化和发布动作必须校验预期旧状态，不能无条件更新。

旧游客资料不自动变成实名账号。数据库迁移采用先加兼容字段、回填、切换读取、最后移除旧字段的方式，部署前在备份副本演练；未知或缺失原数据不能伪造为已确认。

保留期限按数据类别制定，账务与审核证据不能跟随普通头像或草稿的删除规则。具体期限在文档 16 的上线核查完成后配置，未配置时不得宣称已满足保存义务。
