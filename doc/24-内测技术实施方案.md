# GameHub 内测技术实施方案

日期：2026-11-10。版本：0.1，保留原实施基线；当前交付见文档25、26。

实施更新：用户已要求按本方案开始开发；当前交付与实测结果见 [实施进展与验证记录](./25-实施进展与验证记录.md)。下文保留方案形成时的设计状态，不作为各模块已实现的证明。

本文将既有设计细化为可以拆分开发任务的方案，依据制定时的工作区代码与 `doc/01—23`。产品基线沿用 D001—D022，新增工程选择属于建议或授权制定的常规细化，不追加用户确认记录。本文现状章节是方案制定时的快照；后续已并行实施，可执行服务、迁移、测试和仍待配合事项以 [任务清单](./26-实施任务清单.md) 为准，未开通付费资源。

## 一、实施结论与范围

采用 **TypeScript 模块化业务 API + PostgreSQL + 私有对象存储 + 独立任务执行器 + 服务器权威房间 + 独立游戏资源站点**。保留现有 Vite 前端、12 款官方玩法及规则测试，按 B0—B3 逐步迁移。

本轮交付受控内测闭环：测试准入 → 游客游玩 → 手机号账号创作 → 上传或 AI 生成 → 草稿预览 → 人工审核 → 内测目录发布 → 游玩反馈 → 修复复测。

内测使用测试点数，真实收款关闭。短信、模型先实现模拟适配器；只有配置实际提供方与成本预算后才允许真实调用。正式实名、商业收费、公开资格仍按文档 16、20 在后续阶段处理。

文档 22 的 F01—F07 保持候选，不自动进入 B0—B3。现有存档、草稿恢复、反馈和导出任务查询属于已承诺基线，不能作为候选功能省略。

## 二、现状与复用边界

当前实际基线：

- `package.json`：Vite、TypeScript、Node.js；运行依赖只有 `ws`，尚无业务 API 框架或数据库客户端。
- `apps/web/src/main.ts`：网页默认创建 `network: "p2p"` 房间。
- `services/rooms/server.ts`：HTTP/WebSocket 服务，同进程内存管理房间，向 `work/rooms` 保存 JSON。
- `packages/games/core.ts`：已有 `create / act / display / timeout` 规则抽象。
- `packages/host-game.ts`：已有状态复制、动作回执及玩家视图；状态复制有助于避免部分更新，但尚无跨进程事务和租约提交。
- `packages/games/registry.ts`：静态导入受信任官方规则。
- `apps/web/src/platform/catalog.ts`：静态游戏目录。

复用规则、玩法测试、视觉资源、移动端布局和通用游戏界面；新增身份、目录、工作台等平台模块。吹牛骰子在现有引擎中有专门分支，迁移时单独适配，不能假定 12 款游戏全部直接符合通用接口。

不将旧游客 token 当作账号，不将 JSON 房间快照改造成账本，不将用户上传规则追加到静态注册表。旧 P2P 模式作为官方游戏过渡路径保留，用户上传多人游戏只走新服务器权威路径。

当前工作区有大量既有未提交修改与新增文件。实施前记录代码基线和必要备份；不能执行覆盖式重置或以 Git HEAD 代替实际工作区作为迁移依据。

## 三、工程选型

### 3.1 前端与仓库

沿用 TypeScript、Vite 和当前 DOM 渲染方式，按路由、页面状态与服务访问层拆分 `main.ts`。内测不同时引入前端框架重写。后台使用独立 Vite 入口和独立会话，能够复用无权限含义的 UI 部件。

保留 npm 与现有锁文件，按需组织 npm workspaces；不同时切换包管理器。公共契约不得导入服务端配置、数据库或凭据模块。实施时锁定已验证的依赖版本与运行镜像摘要，不在本文猜测最新版本。

### 3.2 业务 API

建议采用 **Fastify**，将账号、目录、版本、审核、任务、钱包、反馈实现为业务模块；框架负责路由、请求校验、响应序列化和请求关联 ID，领域服务负责权限和状态转换。

平台维护的 JSON Schema 作为 HTTP/消息校验的主要来源，生成 TypeScript 类型和 OpenAPI，CI 检查生成物无漂移。游戏上传的参数描述不直接成为框架动态编译的服务端 Schema。

依据：Fastify 官方提供基于 Schema 的校验与序列化，并提醒 Schema 应视为应用代码，不能使用用户提供的任意 Schema。[官方文档](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/)

### 3.3 数据库与迁移

使用 PostgreSQL；建议以 **node-postgres（pg）+ 参数化 SQL + 编号 SQL 迁移** 起步。事务和约束显式表达，避免在账本与房间提交中隐藏锁行为。

统一 `withTransaction` 边界：从连接池取得一个客户端，所有事务语句共用该客户端，失败回滚并释放连接。迁移登记版本和文件摘要，使用独立迁移身份及互斥锁；已应用文件不可修改，只追加修正迁移。迁移脚本禁止在每个 API 实例启动时无条件并发执行。

依据：node-postgres 要求同一事务使用同一客户端，不能用分散的 `pool.query` 调用组成事务。[官方文档](https://node-postgres.com/features/transactions)

### 3.4 异步任务与 Redis

首轮以 PostgreSQL 持久化任务、outbox、租约与消费结果，独立 worker 轮询领取。Redis 为可选优化，不是启动必需组件；需要多节点限流、缓存或更高分发吞吐时再加入。

领取任务使用短事务和 `FOR UPDATE SKIP LOCKED`，仅用于队列竞争领取，不用于跳过余额、审核或房间一致性检查。任务事实与最终结果始终留在 PostgreSQL。

依据：PostgreSQL 指出 `SKIP LOCKED` 适合多个消费者访问队列表，但它提供的视图不适合一般一致性查询。[官方文档](https://www.postgresql.org/docs/current/sql-select.html)

### 3.5 存储、执行与测试

对象存储通过 `put / head / get / delete / issueUploadGrant` 等有限接口封装，供应商待部署时选定。源码、隔离上传区和构建产物均私有；下载不能绕过平台的授权与撤销检查。

独立 Linux 工作节点优先验证 gVisor `runsc`；普通 Docker、Node `vm` 和本机进程不是本方案的不可信代码安全边界。Windows 可继续做前端及业务开发，沙箱通过 Linux 验证环境接入；运行时未通过验证前不得接收不可信服务端代码。

gVisor 官方提供 Docker 集成路径；是否满足本项目的浏览器检查、构建和规则运行，仍需原型实测。[官方文档](https://gvisor.dev/docs/user_guide/quick_start/docker/)

保留现有 `node:test` 与 Playwright，新增真实 PostgreSQL 集成测试和沙箱攻击样例。文档阶段不因新增方案而编写与功能无关的形式测试。

## 四、模块和部署边界

### 4.1 代码归属

- `apps/web`：大厅、运行外壳、创作者工作台。平台外壳持有用户会话，游戏 iframe 不持有。
- `apps/admin`：审核、测试邀请、点数发放、故障反馈和审计页面。
- `services/api`：模块化业务服务及事务；模块包括 access、identity、catalog、projects、versions、reviews、wallet、ai、feedback、operations。
- `services/rooms`：连接票据、房间成员、动作排队、权威状态提交、重连和下架传播。
- `services/ai-worker`：模型适配、需求与产物编排、供应商调用记录；不在进程内构建生成代码。
- `services/artifact-worker`：新增计划模块，协调扫描、构建、导出及回收任务；实际处理不可信文件的步骤交给隔离节点。
- `services/game-runner`：执行控制器，启动沙箱并转交受限 RPC；用户代码只存在于沙箱。
- `services/assets`：新增计划模块，提供游戏资源授权与响应头控制，不向浏览器暴露私有桶的永久地址。
- `packages/contracts`：HTTP、WebSocket、内部 RPC 和错误代码。
- `packages/game-sdk`：iframe 消息桥、客户端 SDK、清单校验与样例。
- `packages/games`：官方规则及兼容适配器。
- `infra`：数据库迁移、环境配置、部署、备份与恢复脚本。

目录代表职责，不要求每个目录首日单独部署。API 与受信任协调进程可共享控制面主机；不可信执行节点必须隔离。先完成可运行的纵向切片，不创建大量空服务。

### 4.2 部署拓扑

浏览器访问平台站点及业务 API；受信任页面连接房间网关。游戏内容从不同站点加载到受限 iframe，经 SDK 消息端口向平台外壳提交动作。房间网关调用隔离执行器，完成候选计算后向 PostgreSQL 提交状态，再向各玩家推送投影视图。

控制面连接数据库、对象存储和必要外部供应商。执行节点只收到当前任务输入、资源上限和有限输出通道，不获得数据库、手机号、账本或支付凭据。

实际内测至少有控制面与隔离执行两个独立安全边界；数据库、对象存储可采用独立服务。是否托管、具体主机数量及规格以原型测量决定。暂不引入 Kubernetes 作为首发前提。

开发、内测、公开环境使用独立身份、数据库、对象空间、队列和密钥。游戏站点使用不同注册域；主站和后台会话采用各自 host-only Cookie，不使用覆盖所有子域的登录 Cookie。

## 五、数据与一致性实施约定

### 5.1 物理字段约定

主键使用 UUID，时间使用 `timestamptz`，状态使用受约束的文本值，文档与规则快照使用有大小上限的 JSONB。所有可竞争更新对象有非空 `revision`，任务与运行授权增加非空 `environment_id`、`generation`。

点数、金额和累计供应商成本使用整数列；不同币种和计量单位明确分开。为了保持现有 JSON 数字契约，API 限制为安全整数范围，数据库读取后进行有界转换；禁止对任意 `bigint` 无条件转成 JavaScript `number`。提供方原始小数费用按其精度保存或保守向上换算，不能浮点累加。

初始迁移按依赖拆分：环境/身份 → 作品/版本/资源 → 发布/审核 → 任务/点数/成本 → 房间/存档 → 反馈/审计/回收。支付正式运营扩展放在相应阶段，不要求 B0 建完所有商业表。

### 5.2 必须落库的约束

- 点数账户及批次各余额非负；账户汇总与批次分配通过事务更新并定期核对。
- `(game_id, version_number)` 唯一；版本所属游戏、作者和发布引用使用外键及事务校验。
- 一个游戏最多一个有效审核申请，以部分唯一索引保障。
- 发布生效指针按 `(environment_id, scope, game_id)` 唯一。建议独立 `publication_heads` 表承载指针，`releases` 保留发布历史；避免让 `games.current_release_id` 成为跨范围共用字段。
- 请求幂等键按主体、操作域唯一并绑定请求摘要；最终财务动作另有业务唯一键。
- 同一个任务只有一个冻结终结记录，结果为结算或释放之一；仅为两种动作分别建唯一键不能保证互斥。
- `(room_id, action_id)` 唯一，记录发起成员、请求摘要和结果；同 ID 换人或换内容必须拒绝，不能返回他人的处理结果。
- 云档按 `(user_id, game_id, save_schema_version)` 唯一，写入及删除都使用预期 revision。
- 事件去重按 `(consumer, event_id)` 唯一；渠道交易、渠道事件、通知接收日志分别建模。

`publication_heads` 与冻结终结记录是对文档 11 逻辑模型的物理细化建议，正式迁移前同步回模型及契约，不声称现有代码已经支持。

### 5.3 事务边界

创建 AI 任务：校验环境世代、报价及工作区 revision，锁定账号、报价和点数账户，按统一顺序锁批次，创建冻结分配、任务、幂等结果与 outbox，整体提交。报价只能被同一确认任务消费；重复提交返回原任务。

成功结算：先确认私有对象已可靠写入并核对摘要，再在一个事务中复核任务状态、执行标识、环境世代及作品可写性，登记候选版本、检查证据、冻结终结记录、扣点流水和成功状态。对象上传成功但事务失败时，可由仍有效任务重试提交；无引用对象后续回收。

失败、取消与超时：通过同一个冻结终结约束完成释放；超时扫描器和成功回调竞争任务状态，只有一方提交成功。终态不得再次收费。

发布：锁发布指针及游戏限制，复核版本检查、审核快照和当前环境范围，提交新指针、发布历史、审计和 outbox。新版本只影响新启动会话，旧房间保持固定版本。

统一锁顺序形成工程约定，并在涉及多个模块时复用同一事务上下文；网络调用和沙箱计算不占用长事务。死锁及可重试冲突采用有限次数重试，外部调用不得随数据库事务盲目重放。

## 六、关键链路实现

### 6.1 测试准入与账号

`POST /test-access/exchanges` 只验证邀请及限流，通过条件更新原子占用兑换次数，再建立测试访问会话；后续业务请求先校验准入，再校验游客、账号或后台权限。

手机号短信先用白名单模拟提供方。挑战只保存验证码的受保护校验值，按挑战限制失败次数、有效期与单次使用；注册与绑定依靠唯一约束防止同手机号并发创建重复账号。

主站和后台会话独立，数据库保存会话摘要与撤销状态。HTTP 修改操作校验 CSRF 与 Origin，WebSocket 校验平台 Origin 和单次票据。测试邀请不发后台角色，房间邀请不赋予测试访问资格。

### 6.2 上传、预览与发布

1. 创建上传意图，绑定作者、用途、大小和摘要；文件进入私有隔离区。
2. 完成回调读取真实对象信息，创建 `artifact_jobs`，不能信任浏览器报告。
3. 在隔离环境执行路径、大小、类型和清单校验；构建只允许批准模板和依赖。
4. 输出内容摘要、不可变资源清单和检查证据；建立草稿版本。
5. 作者通过短期预览会话访问同等隔离环境；预览成功不自动送审。
6. 送审冻结内容和元数据；批准后按发布选项切换内测目录指针。
7. 游玩、导出、资源下载分别重新验证授权；游戏归档、平台限制或任务过期均不能只靠前端隐藏处理。

对象上传与数据库之间不存在跨系统事务；采用“先写对象、核验完成、再提交引用”的顺序，孤立对象有保留窗口和二次引用检查。

### 6.3 iframe 与资源授权

默认 `sandbox="allow-scripts"`，不向 iframe 提供平台 Cookie、API token 或连接票据。父页面创建随机加载标识并核对 `contentWindow`，建立专用 MessageChannel；导航、卸载、下架或会话撤销时关闭端口。

不透明来源下不能以 `origin === "null"` 证明身份。仅初始端口转交可按浏览器要求使用 `*`，该消息不带平台凭据；后续每次桥接请求验证协议、尺寸、能力和当前加载标识。

M0 必须验证模块脚本、相对资源、字体、存档和 CORS。默认不支持的包返回明确原因；需要真实来源的兼容类型，必须按版本或游戏分配隔离来源并单独验证，不全局增加 `allow-same-origin`。

跨站嵌入不依赖第三方 Cookie。建议使用短期、仅能读取固定版本资源的游戏资源能力，绑定运行会话、环境世代和到期时间；资源网关逐次检查撤销状态。该能力不是账号凭据，采用 `Referrer-Policy: no-referrer`，访问日志不记录明文能力。

资源能力可能被持有人复制，不能声称浏览器内文件不可获取。测试入口网关还需保护资源域，复制资源链接不能替代测试准入。涉及跨站授权的真实浏览器兼容性列为 M0 门槛，未验证前不开放外部测试邀请。

缓存不可变文件字节，但缓存命中前仍须授权；不提供绕过网关的公共桶地址。强制下架可停止平台新资源请求、连接和服务端状态推进，无法追回已下载文件，也不能承诺离线浏览器里的 JavaScript 立即停止。

### 6.4 权威房间与规则执行

房间固定不可变版本。网关从连接身份附加 playerId，动作 ID 与请求摘要一起校验；每房间串行调度，其他房间独立。

处理顺序：

1. 验证运行授权、成员、动作结构、速率和去重记录。
2. 获取房间当前 `sequence`、`leaseEpoch` 和快照；复制状态并把有限 JSON 输入交给沙箱。
3. 沙箱调用规则，产生候选状态。旧 `act` 可在候选副本中原地修改，不接触数据库中的已提交状态。
4. 校验输出大小、结构和运行限制；规则异常、超时或越界丢弃候选。
5. 提交事务重新校验当前环境世代、限制、租约所有者、租约有效期、`leaseEpoch` 及预期序号。
6. 原子写入状态、事件、动作结果和新序号。提交后才确认动作及推送玩家视图。

初期状态体积上限按文档 08，建议事务内保存当前快照 JSONB，历史归档再写对象存储，减少初始双存储提交路径。完整状态限制服务身份读取，备份与静态存储加密，日志不记答案。

`display` 在状态副本上执行，其返回值只发给指定玩家；失败不发送完整状态替代。投影尺寸和结构可机器校验，是否泄露玩法秘密还需官方游戏测试及上传规则审核，不能声称通用 Schema 能判断所有私密语义。

时间来自平台确定的动作上下文；随机数在隔离侧由平台控制的适配器提供，规则不能从玩家请求取得随机源。恢复以已提交快照为依据，记录必要随机状态；不依赖任意用户代码必然可确定性重放。

房间主持租约与玩家房主角色分开。租约丢失的旧执行器即使返回成功也不能提交；同一动作提交成功而确认丢失，重试返回已记录结果。玩家重连先校验版本仍可运行，再获取本人最新视图。

### 6.5 AI 编排与两套额度

AI 业务状态固定为排队、执行中、成功、失败、取消、超时；模型调用、构建、浏览器检查等作为执行步骤，不额外创造可以绕过结算的业务终态。

对外任务提交只接受已确认报价 ID；报价绑定需求快照、工作区 revision、模板、基线版本和固定点数。任务创建与冻结见第五节。

worker 领取时更新执行标识与租约；模型调用前另行事务性申请提供方成本预留。日额度与月额度必须共同检查，预留覆盖本次调用上限、潜在重试及执行成本；用户点数充足不代表可以绕过成本限额。

模型适配器提供生成、查询结果、用量归一化和错误分类；只有服务商确实支持时才实现幂等重试或取消。对无法确认是否执行的超时调用保留费用预留，先查询或人工核对，不直接再次调用。

AI 输出视为不可信代码，进入与上传同等的检查链。成功后只新增候选版本，由作者选用，不覆盖后来保存的草稿；任务成功、内容审核通过与公开放行是不同状态。

提供方持续故障或预算不足时停止新真实调用，返回明确原因；排队与执行超时沿用文档 18，不无限等待。免费修复也计入真实预算。

### 6.6 草稿、存档与反馈

工作区自动保存使用 `expectedRevision`；冲突保留本地待保存内容并显示服务端 revision，不静默覆盖。恢复历史快照产生新快照，不能修改审核版本或自动回滚发布指针。

云档身份、游戏与结构版本从运行会话取得；游客本地档由平台外壳管理。登录导入须明确选择且校验目标 revision；旧结构档独立保留。

反馈保存准确游戏版本、环境、房间或任务关联；附件使用游客专属受限上传入口，不复用作者源码权限。处理记录关联修复版本和复测结果，只有提交者、相关作者及授权处理人可访问相应内容。

## 七、任务领取、撤销与故障恢复

任务、outbox 及租约时间均以数据库时间为准。领取在短事务内更新执行标识和到期时间；执行期间心跳续租，完成提交重新核验。队列消息可以重复，不能把“消息已消费”视为业务已成功。

消费者在业务变更的同一事务中登记去重结果；先标记消息完成再执行业务会造成不可恢复的漏处理。外部效果使用已持久化意图和提供方幂等键；无幂等支持时进入结果核实流程。

强制下架同时修改游戏限制并写事件，网关主动推送且定期回查。建议原型以 2 秒回查、最长 4 秒授权缓存作为测试起点，验证正常网络下 5 秒传播目标；控制面失联时不无限续期。主动下架的老局宽限与强制下架立即撤销按文档 04 分开。

测试重置先停止准入与任务领取，明确处理冻结、调用和运行会话，再递增环境世代。所有结果提交以事务内世代复核为准；旧票据、旧执行结果和旧下载授权不能写回。提供方未核实费用与必要审计不能因重置被删除。

恢复时先恢复数据库和对象引用一致性，再检查 outbox、任务租约、冻结和运行授权；余额不能通过回滚数据库后直接宣称已经与外部系统一致。

## 八、B0—B3 开发任务与退出条件

### B0：工程基础与高风险验证

**B0-01 契约和工程骨架。** 提取公共契约包，建立 Fastify API、数据库迁移命令、配置校验及模拟提供方。保留旧启动入口。交付最小可运行服务和 CI，不创建无用途空模块。

**B0-02 测试身份。** 完成测试邀请、兑换、撤销、游客会话、账号权限边界和环境世代。对应 INT-01、INT-02、AUTH-01、AUTH-04。

**B0-03 运行隔离原型。** 使用静态上传样例、Vite 样例及恶意消息样例验证独立站点、资源授权和 SDK 握手；使用死循环、文件越界、出网及超限输出验证 Linux 执行节点。对应 PKG-02—06。

**B0-04 数据与成本基础。** 完成任务/outbox、测试点数、冻结终结约束、模拟支付隔离、供应商预算和最小重置流程。对应 INT-04—06、AI-02、AI-10。

退出条件：测试入口不可绕过；不可信代码没有宿主或控制面凭据；账本重复操作与成本开关验证通过；提供原型证据及未支持包类型。任何隔离原型失败必须修复或缩小能力，不能用人工审核代替。

### B1：官方游戏与单人上传闭环

**B1-01 账号和动态目录。** 实现手机号测试登录、作者工作台、数据库目录、官方游戏 ID 映射。对应 AUTH-02—06。

**B1-02 上传及版本。** 实现上传意图、扫描任务、不可变版本、检查结果和草稿保存；刷新可恢复任务。对应 PKG-01、PKG-07—08、DRAFT-01。

**B1-03 预览审核发布。** 实现最小审核后台、内测发布指针、启动授权、主动/强制下架。对应 PUB-01—08。

**B1-04 游玩和反馈。** 接入一款官方游戏及一款独立上传单人样例，实现云档、本地档与最小问题反馈。对应 SAVE-01—02、FEED-01。

退出条件：受邀游客可以体验；作者不改主站注册表即可上传并发布新游戏；审核前不可目录启动，撤销后旧链接不能重新授权；多人及 AI 尚未完成的入口明确不可用。

### B2：多人上传与 AI 创建修改

**B2-01 房间事务与适配。** 实现权威房间、连接票据、隔离规则 RPC、动作去重、持久化提交和重连。对应 ROOM-01—04A、ROOM-06。

**B2-02 AI 垂直链路。** 完成报价、冻结、模型适配、构建检查、候选版本、失败释放、导出查询和免费修复。对应 AI-01—10、PKG-08、DRAFT-01—02。

**B2-03 代表性样例。** 一款上传多人游戏独立完成开局到结束；一个 AI 创建任务和一个已有源码修改任务完成预览、审核及回归。模型先用模拟适配器验证编排，再在已批准预算内验证真实质量。

**B2-04 竞争故障。** 注入租约转移、重复回调、提交后断连、模型超时、取消竞争、对象落盘后事务失败。记录账本、版本、房间和客户端最终一致的证据。

退出条件：新包无须改主站即可多人运行；不重复应用动作、不重复扣点、不静默覆盖草稿；真实模型未开通时只能声明模拟链路通过，不能声明 AI 生成能力完成验收。

### B3：官方全量迁移与内测验收

**B3-01 逐款迁移。** 保留官方 ID、人数、观战、私有信息、断线与玩法语义；吹牛骰子单独适配，其他游戏按接口复用。对应 ROOM-05。

**B3-02 反馈闭环及生命周期。** 完成修复版本关联、复测、归档恢复、资源保护与回收。对应 FEED-02、PKG-09、INT-07。

**B3-03 运维和容量。** 以 100 在线、20 活跃房间、2 并行 AI 为初始目标验证延迟、故障、成本及恢复；报告设备与网络条件。对应 OPS-01—03 和文档 13 容量门槛。

**B3-04 切换与回退演练。** 在受控测试目录逐款切换，验证旧局退出、新局建立及失败回退。内测问题不留核心流程阻断；扩大测试前完成 12 款官方游戏回归。

依赖关系：B0 是 B1/B2 的安全与数据前提；B1 版本及资源契约稳定后，房间和 AI 可分别开发，再在 B2 汇合；B3 汇总回归。无团队投入数据，不编造人日或日期承诺。

## 九、迁移与回退

1. 记录实际工作区基线，保留现有测试、启动脚本和官方游戏数据。
2. 新数据库和新 API 在独立开发/内测环境运行，不原地覆盖 `work/rooms`。
3. 为官方作者及 12 款游戏导入元数据和首个版本，维护旧 ID 映射；先接入一款试点。
4. 新平台外壳逐步改为 API 目录，老 P2P 入口只用于仍未迁移的官方游戏。
5. 迁移游戏先停止创建旧局并通知结束，旧局不跨架构搬迁；受控目录切换至新版本。
6. 回退通过关闭新入口、恢复仍获准的旧官方服务完成；不向旧服务灌入新账号、UGC 或点数数据。

代码回退和数据库恢复分开：采用扩展字段、回填、切换读取、最后收缩的迁移策略，优先前向修复。已完成点数动作不能靠数据库整体回退撤销。平台强制限制与已撤销版本在回退路径上仍必须生效。

## 十、验证与交付清单

每个开发切片至少交付实现代码、迁移、契约、可运行样例、相应自动化测试及结果证据。CI 包含类型检查、现有玩法回归、Schema 一致性、真实数据库约束/事务测试及必要浏览器流程；沙箱测试在独立 Linux 环境执行。

关键并发测试必须真的产生并发和故障：余额不足竞争、同冻结结算/释放互斥、同报价重复任务、旧租约提交、重复动作不同请求、草稿 revision 冲突、下架事件丢失和测试世代切换。

运行检查记录 `requestId / taskId / attemptId / gameVersionId / roomId / sequence`，不记录手机号、验证码、访问凭据、完整题目答案或模型密钥。监控任务年龄、最老 outbox、租约异常、冻结差异、成本已用加预留、资源拒绝及房间提交延迟。

性能目标沿用文档 10：普通 API p95 < 500 ms、房间动作处理与回传 p95 < 300 ms，均需约定网络及负载；规则调用 500 ms 为硬上限而非性能目标。生产 99.5% 可用性、RPO 15 分钟、RTO 4 小时是后续配置与演练目标，不能以单台主机部署文档证明达成。

当前仅完成文档与代码事实核对；以上任何新平台用例都未因本文存在而标记通过。
