## 容量测量与限制

协调暂停其他测试后，完成三档房间基线及两组100人目标样本。20个房间、每房5人、两个模拟执行循环并行时：

- 池上限10：100次动作，推送 p95 **322.09 ms**，HTTP/WS 零错误。
- 池上限20：100次动作，推送 p95 **290.86 ms**、p99 327.56 ms，HTTP/WS 零错误，8项模拟任务全部完成，任务运行并发峰值2。

池20的测量段仅2.53秒；它只证明这次小状态官方规则短样本低于300ms目标。50个双人房间的池10样本 p95 仍为984.80ms，完整容量门槛不能宣告通过。没有覆盖长稳、慢客户端、广域网/TLS、真实 AI、复杂用户规则或多实例房间转发。

本机 `.env` 采用已测过的池上限20；仓库默认和 `.env.example` 仍为10，不将一次样本推广到其他部署。原始数据 `work/platform/capacity.json` 保留初测受并行任务干扰的说明。更多复现命令及条件见 [房间与性能](../docs/platform-rooms.md)。

## 当前环境与启动

本机 Node.js v24.21.0、Docker PostgreSQL 18.6 固定镜像；独立项目 `gamehub-platform-dev`，数据库监听 `127.0.0.1:55432`。开发库已应用0001—0011迁移并初始化12款官方作品。未替用户建立普通或超级管理员账号；可按开发文档通过白名单登录后显式授予角色。

## 尚未完成的范围

真实短信、真实 AI、真实支付均未接通，开关保持关闭。模拟 AI 输出固定计数器，只验证编排和结算，不实现自然语言需求。用户上传服务端规则、任意构建和自动执行不可信产物的质量流水线未开放；worker thread 与普通容器不是强沙箱。

官方房间当前应采用单 API 实例；租约和恢复不等于多实例透明转发，普通连接粘性也不能确保所有玩家到同一房间主持。自定义图片头像、无法验证旧手机号的人工找回、实际注销匿名化、最终历史版本销毁、真实渠道退款和正式监控仍有明确缺口。

需要用户提供独立 Linux/gVisor 节点、模型/SMS/支付供应商资源及预算、独立 HTTPS 站点和部署资源、留存与退款/找回政策及运营责任人。之后还要完成适配和验收，并非仅填密钥即可上线。详细任务和配合项见文档26。
