# 技术架构与迁移方案

状态：授权制定的技术设计，未实施。默认小规模试运营，容量以压测为准。核心技术依据见 [文档 17](./17-技术选型依据.md)。

当前目标为受控内测（D022），按文档 20 分离内部与公开发布范围、测试账本和外部真实成本。部署模式及环境世代由服务端配置，浏览器无法改写；正式实名与商户接入不作为内部原型的先决条件。

## 一、架构选择

采用模块化单体业务 API，加独立的任务执行和游戏运行服务。首发不拆分大量微服务，但必须分离不可信代码执行、用户游戏资源和资金业务。

继续使用 TypeScript、Vite 与 Node.js。现有 UI 保留可复用部件，按路由和业务模块演进，不为文档阶段强行引入新前端框架。生产实现选定受维护版本并锁定依赖，不把当前本机版本永久写成生产要求。

PostgreSQL 保存账号、作品、版本、审核、任务、账本、订单和审计事实；对象存储保存源码及构建物；Redis 用于限流、短期会话协调和队列加速，不能作为余额或订单的唯一事实来源。

## 二、模块边界

业务 API 负责身份会话、权限、目录、作者操作、审核、点数和支付。模块之间通过明确服务接口交互，禁止在 UI 请求中直接执行游戏或构建代码。

AI 编排服务负责报价、任务调度、模型适配、产物收集、运行检查和状态推进。模型适配层统一输入输出、用量和失败类型，服务商替换不改账本规则。

构建与预览执行器处理用户源码和模型生成物。它们只接收任务必要材料、有限时效的读写授权，不拥有支付、用户手机号或数据库超级用户凭据。

房间网关处理连接、身份、动作序号、限流与下架信号；游戏执行器处理隔离的规则计算，返回各玩家投影视图。用户代码不得成为网关模块。

资源网关在游戏独立站点提供受控资源。平台主站、后台和游戏站点分开认证域，游戏 Cookie 不能成为平台会话。

## 三、不可信执行隔离

构建、浏览器检查和服务端规则使用独立 Linux 执行节点与强隔离运行时；设计首选 gVisor 类沙箱，按目标云环境验证，必要时改为微虚拟机方案。普通进程、Node vm 或单纯线程隔离不作为不可信代码的安全边界。

每次构建使用临时工作区、只读基础镜像、非特权用户、资源上限和超时；任务结束清理可写层。禁用宿主目录挂载、Docker socket、宿主网络及云元数据访问；依赖获取由受控阶段完成。

多人规则执行器按房间或隔离租户分配运行环境，固定版本且无任意网络访问。每次调用都校验输入输出大小、调用时限和租约标识；候选状态提交时还必须在事务中重新校验当前租约隔离令牌与预期序号，原子记录状态、事件及动作去重结果，防止调用期间租约失效的旧主持覆盖新状态。沙箱故障仅影响所辖房间，不能影响账本服务。

沙箱能力尚未验证前，不开放用户多人服务端代码执行。该条件属于实现与测试门槛，不以人工审核替代隔离。

## 四、资金及任务一致性

支付入账、点数冻结和任务创建在数据库事务内写事实，同时写 outbox 事件。分发器可重复投递；消费者以业务唯一键去重。不能追求外部回调“只会到一次”，而应让重复到达没有重复财务效果。

账户行按固定锁顺序更新，余额不允许负数；流水与批次分配同事务落库。网络调用不长期占用资金事务，先持久化意图，再调用外部服务并查询确认结果。

任务租约过期可重新领取，执行标识递增。只有仍匹配当前任务状态与执行标识的结果可结算；终态不被旧回调覆盖。每天执行账务一致性核对，发现差异冻结相关写操作并生成工单。

## 五、发布和撤销传播

每个游戏在当前部署范围内具有单一生效版本指针。发布事务校验环境、内部审核及游戏限制；公开范围额外检查公开资格，内测范围检查测试准入策略。原子切换对应指针并写发布事件，不能把内测指针用于公共资源路由。公开资格失效只处理对应范围并按风险另行判定内测，不能把未知资格伪造成有效。资源文件使用不可变摘要键。

异步扫描、构建检查、导出和回收采用统一持久化 job 对象，结果在数据库及受控对象存储中关联；前端刷新后可恢复查询。队列事件丢失可由数据库扫描补偿，下载授权在获取结果时再次校验而不只在创建任务时校验。

所有测试任务、访问会话与结果携带环境世代标识。重置测试环境递增世代并撤销旧凭据，拒绝旧执行器迟到写入；不只清空前端缓存。

每次新开局核验最新限制；资源访问授权绑定版本、会话与时效。下架通过事件通知房间和资源网关，同时网关定期主动校验限制，避免单次通知丢失永久失效。

资源缓存与运行授权分离：可缓存不可变文件，但访问网关仍校验授权与撤销状态。失去控制面连接时不无限延续运行授权。强制下架在正常网络下的传播验收目标为 5 秒内，断网客户端不保证即时收到通知，恢复连接必须先校验。

## 六、联机选择

公开平台采用服务器权威状态，P2P 保留为现有项目的过渡路径，不作为用户上传游戏的默认运行方案。原因是统一审核、强制下架、断线恢复和私有数据控制需要平台可管理的运行点。

这是授权制定的架构选择，不改变已确认的多人功能。它增加服务器运行成本，需在试运营压测中测量房间资源消耗，而不是承诺现有免费隧道可以承载公开平台。

游戏快照写入持久化存储，包含规则版本、序号、上下文和恢复所需信息。恢复必须校验版本仍获准运行；强制下架不能因工作进程重启自动复活。

## 七、建议目录

- `apps/web`：玩家端与创作工作台，逐步从现有页面模块迁移。
- `apps/admin`：后台前端，独立权限入口。
- `services/api`：模块化业务 API。
- `services/rooms`：重构后的房间网关与协调。
- `services/ai-worker`：AI 任务编排与调度。
- `services/game-runner`：隔离执行控制器，实际游戏进程在沙箱内。
- `packages/game-sdk`、`packages/contracts`：受版本管理的客户端 SDK 与接口契约。
- `packages/games`：现有官方规则与迁移适配，不存放未经隔离的用户动态导入代码。
- `infra`：环境配置样例、迁移、部署与恢复脚本；不提交真实密钥。

这些是计划路径，当前不创建空实现来假装功能已完成。

## 八、既有内容迁移

现有 `catalog.ts` 静态目录转为数据库驱动，保留已有游戏 ID 的别名与分享映射。`core.ts` 的规则抽象可复用，`registry.ts` 的静态 import 仅用于受信任的官方包。

旧 `work/rooms` 中的游客 token 不升级为正式账号；旧局不尝试跨架构实时迁移。切换时通知用户结束旧局，再创建新房间，保留必要运行记录并按清理规则处理。

逐款迁移 12 个官方游戏，先在测试环境验证，再通过受控目录切换上线。开发期间现有服务继续保留，不能用数据库初始化破坏原游戏运行。

## 九、非功能设计目标

初始验收负载为 100 名同时在线玩家、20 个活跃房间、2 个同时执行的 AI 任务；不是用户需求上限或当前已具备容量。压测后按实际资源与预算调整。

普通 API 在约定测试网络下 p95 小于 500 ms；游戏动作处理与回传 p95 小于 300 ms，AI 长任务单独测量。第三方支付和短信等待时间分别记录，不能混入平台响应指标隐藏问题。

生产可用性目标初设 99.5% 月度，备份目标 RPO 15 分钟、RTO 4 小时；它们是设计与演练目标，不是未经验证的服务承诺。支付账务应结合渠道对账修复，不能仅靠数据库回退宣称无损。
