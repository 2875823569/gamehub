# 需求参考与取舍依据

核查日期：2026-11-10。以下仅使用产品官方资料；所引页面为持续维护文档，不将抓取时间或 URL 推断为功能发布日期，也不引用价格。

当前阶段为内测，保留游客免账号游玩的产品决定。本文提供需求取舍依据，不将参考产品的功能视为本项目已实现，也不将建议自动升级为用户已批准范围。具体排期以项目需求清单为准。

## 一、受限测试分享：借鉴访问范围，而非只隐藏列表

**来源事实：**itch.io 区分 Draft、Restricted 与 Public。Restricted 可通过访问密钥或密码授权，撤销密钥会失去访问资格；该模式不进入公开浏览、搜索和个人页面。其草稿模式主要用于准备页面，官方并不建议将草稿当作正式分发方式。[itch.io：项目访问控制](https://itch.io/docs/creators/access-control)

**本项目建议：**为内测设置受限的版本分享能力，绑定游戏版本、允许的测试范围、有效期和撤销状态。测试链接只授予运行和反馈权限，不授予源码下载、作者操作或管理权限；多人邀请不能扩大原测试范围。

**价值与优先级：**内测优先。作者能够把尚未公开的版本交给指定测试者，不必先走公开发布，也不必共享作者账号。

**成本与边界：**隐藏搜索结果不等于访问控制。需要资源、启动、房间和重连共同校验权限；链接失效后也应停止新的启动。是否为特定版本开放测试，由现有内测规则明确，不能因此跳过包检查与隔离。

## 二、自动保存：保护尚未形成正式版本的工作

**来源事实：**Construct 3 的设置提供周期性项目备份、备份位置和间隔选项，用来减少崩溃或硬件故障造成的丢失。[Construct 3：Save & backup 设置](https://www.construct.net/en/make-games/manuals/construct-3/interface/dialogs/settings)

**本项目建议：**对需求描述、元数据和作者正在编辑的工程保留自动保存状态；显示“已保存／保存中／保存失败”。任务提交前固定一份输入快照，页面刷新后可以继续编辑尚未提交的内容。

**价值与优先级：**内测优先。AI 创作过程通常经历多轮描述和调整，丢失输入比缺少社交功能更直接破坏体验。

**成本与边界：**自动保存不自动公开、不自动送审，也不能覆盖已审核版本。需要容量和保留策略、并发版本检查与恢复入口，不能把本机浏览器缓存称为可靠云备份。

## 三、自己的工程恢复点：让 AI 修改可比较、可撤回

**来源事实：**PlayCanvas 的版本控制通过检查点记录工程状态，可查看历史并恢复过去状态；分支用于隔离修改，合并有独立的冲突处理流程。[PlayCanvas：版本控制](https://developer.playcanvas.com/user-manual/editor/version-control/)

**本项目建议：**在 AI 修改前保留作者自己的工程恢复点，完成后展示“改了哪些文件、增加了哪些资源、主要玩法发生什么变化”。作者可以选择保留新结果或从旧状态生成新的草稿，而不删除后续历史。

**价值与优先级：**紧随基本内测闭环。它让用户敢于尝试修改，也能为“AI 没按需求完成”的问题提供证据。

**成本与边界：**先做版本摘要、文件差异和恢复草稿，不做完整 Git 分支与多人冲突编辑器。大资源差异以摘要与预览表示，避免无意义地展示二进制内容。恢复草稿与切换线上版本是不同动作，后者仍遵守审核和发布规则。只处理作者自己的工程，不开放复制其他作者作品。

## 四、可定位的调试结果：先让问题说得清楚

**来源事实：**GDevelop 的调试器可在预览时检查变量和对象状态、暂停游戏进行检查；其性能分析工具用于查找运行过程中耗时的部分。[GDevelop：Game Debugger and Profiler](https://wiki.gdevelop.io/gdevelop5/interface/debugger/)

**本项目建议：**先提供简化的创作者诊断面板，汇总启动失败、资源加载失败、未处理异常、SDK 协议错误和当前版本。测试者提交问题时，经明确选择附带脱敏诊断摘要、设备信息、版本与操作描述，形成作者可处理的反馈记录。

**价值与优先级：**内测优先，优于立即建设完整断点调试器。它可以把“打不开”“点了没反应”转化为能复现的问题。

**成本与边界：**平台无法替任意引擎自动解释内部变量，更不能让调试器读取其他玩家的私有数据。首版不默认上传截图、完整对话、源代码或完整日志；错误栈和文件名可能含敏感信息，应脱敏并按角色展示。

## 五、启动与性能报告：分清加载慢、卡顿和运行失败

**来源事实：**PlayCanvas Profiler 分开展示帧率、更新与渲染耗时，并在时间线上表示页面解析、资源预加载和开始运行等阶段，资源加载也有独立记录。[PlayCanvas：Profiler](https://developer.playcanvas.com/user-manual/optimization/profiler/)

**本项目建议：**首先测量点击开始到游戏就绪的时间、启动成功率、缺失资源和关键错误；进一步提供包体大小与主要资源占用。多人游戏增加连接成功率和断线重连结果。帧率作为可选指标，避免把后台标签页节流误判为游戏故障。

**价值与优先级：**基础启动指标适合内测，完整性能分析面板后置。先找出用户无法进入游戏的原因，再优化复杂图形性能。

**成本与边界：**不同浏览器、设备与沙箱能观察到的数据不同，必须记录测量条件和样本数；不能照搬特定引擎的内部 CPU/GPU 分类，也不能对未测量指标显示虚构分数。

## 六、建议实施顺序

第一批以“受限版本测试、自动保存、问题反馈与诊断摘要”为主，确保能测试、能复现、能修复。

第二批补“自己的工程差异与恢复、启动质量报告”，增强创作信心并识别体验瓶颈。

完整可视化调试器、多人实时协作、复杂分支合并和引擎级性能分析暂不优先；这些功能会明显增加技术面和维护成本，当前资料不能证明它们比内测反馈闭环更有价值。

以上顺序是针对本项目现阶段的设计判断，不是来自竞品资料的市场结论。实际采用后应观察启动成功率、有效反馈比例、问题复现率、修复耗时及创作者继续修改的比例，再决定投入。
