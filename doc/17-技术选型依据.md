# 技术选型依据

核查日期：2026-11-10。状态：官方资料核查与设计依据，未进行部署或性能验证。本文引用滚动更新的官方文档，不据此宣称某个版本为项目应采用的最新版本。

“资料事实”表示来源明确说明的能力或限制；“项目设计”表示基于这些事实作出的方案选择，仍需实施和验收。

## 一、现有代码能复用什么

现有项目使用 TypeScript、Vite、Node.js 和 `ws`，可保留语言、构建及玩法测试基础，不需要为扩展平台而整体替换技术栈。依赖见 [package.json](../package.json)。

[packages/games/core.ts](../packages/games/core.ts) 已定义 `create`、`act`、`display` 和可选 `timeout`，并把时间与随机数通过上下文传入。其思想适合作为多人逻辑的适配起点，但当前 `act` 会直接修改状态，协议迁移需明确事务提交和失败回滚，不能只改函数名称。

[packages/games/registry.ts](../packages/games/registry.ts) 静态导入官方规则；[packages/host-game.ts](../packages/host-game.ts) 和 [services/rooms/server.ts](../services/rooms/server.ts) 直接使用这些规则。这是受信任官方代码的集成方式，不是可直接接收用户代码的插件沙箱。

[apps/web/src/main.ts](../apps/web/src/main.ts) 创建房间时选择 P2P；[apps/web/src/peer-transport.ts](../apps/web/src/peer-transport.ts) 将恢复快照保存在浏览器会话中；房间服务把数据写入 `work/rooms`。这些机制可以作为旧游戏迁移资料，不能充当充值账本、账号持久化或不可信多人游戏的安全边界。

项目设计：将平台账号、游戏目录、点数和发布业务与游戏执行分开；官方规则通过适配器接入新运行协议。保留现有游戏玩法及测试，不把用户上传代码直接追加到原静态注册表。

## 二、网页游戏隔离

### 2.1 iframe 与站点边界

资料事实：`sandbox` 可限制脚本、表单、弹窗等能力；不设置 `allow-same-origin` 时，嵌入页面具有特殊来源。MDN 特别提醒，同源父子页面同时开放脚本与同源能力可能破坏沙箱约束；独立来源还可降低游戏被单独打开时的风险。[MDN：iframe](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe#sandbox)

项目设计：

- 平台网页与游戏内容使用不同站点；游戏内容站点不共享平台登录 Cookie，不承载后台页面或账号 API。
- 预览与公开游玩使用同样的隔离边界，审核员浏览用户游戏也不能绕过隔离。
- 默认仅开放必要脚本执行；不开启顶层导航、任意弹窗、表单提交和下载等权限。全屏等能力按明确的游戏声明和平台交互授予。
- 不向游戏提供平台登录令牌、手机号、钱包接口或后台凭据。游戏只获得该会话所需的脱敏信息和有限能力。
- 具体包格式必须与隔离策略兼容；例如 opaque origin 下的模块加载、资源读取和持久化需验证，不能先宣称任意网页包都兼容。

### 2.2 消息桥不是信任授予

资料事实：跨窗口消息需核验发送来源、窗口及消息结构；已知目标来源时应指定精确 `targetOrigin`。`MessageChannel` 提供两个端口，并支持向 iframe 转移端口。[MDN：postMessage](https://developer.mozilla.org/en-US/docs/Web/API/Window/postMessage#security_concerns)、[MDN：MessageChannel](https://developer.mozilla.org/en-US/docs/Web/API/MessageChannel)

项目设计：

- 桥接消息只开放白名单操作，例如准备完成、提交本局操作、接收当前玩家视图、报告结束和申请平台控制的全屏。
- 每个请求检查消息类型、结构、长度、速率、当前会话、游戏版本和参与者权限；游戏自己声称“当前用户 ID”不能决定服务端身份。
- 采用无同源权限的沙箱时，来源可能为 `null`，不能把 `origin === "null"` 当作身份认证。握手绑定实际创建的 iframe 窗口、当前加载标识和受限的专用消息端口。
- 如果 opaque origin 的初始端口转移需要 `*`，该步骤不得携带平台凭据或敏感数据；端口只暴露最小化游戏能力，后续导航、卸载和会话撤销立即关闭端口。
- 若未来某类游戏必须保留真实来源，应单独评估按游戏或版本隔离来源的方案，并使用精确目标来源；不能通过把所有游戏迁回平台同源来解决兼容问题。
- 浏览器桥和后台运行授权各自鉴权。即使页面伪造一条“已获准发布”消息，也不能启动草稿或已下架版本。

### 2.3 CSP 是附加控制

资料事实：CSP 可以按资源类型限制加载来源，是防御的一层，而不是替代输入处理和整体隔离。[MDN：CSP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CSP)

项目设计：由平台响应头约束脚本、图片、字体、连接、表单和嵌入来源，游戏包不能自行放宽平台策略。默认关闭直接外部连接，平台游戏操作通过受控桥发送。资源与网络权限绑定审核快照；评论等平台内容仍需编码或清理。浏览器端策略不能替代服务端的出网限制。

## 三、不可信构建与多人规则执行

资料事实：Node.js 官方明确指出，`node:vm` 不是安全机制，不应作为运行不可信代码的安全边界。[Node.js：VM](https://nodejs.org/api/vm.html)

项目设计：AI 生成代码和用户上传代码均按不可信代码处理。构建脚本、依赖安装、浏览器自动检查、多人服务端规则都不得在 API 或账本进程内执行；不能把增加 `vm` 超时等同于完成沙箱建设。

资料事实：gVisor 通过额外隔离层减少系统接口暴露，但沙箱仍可以访问映射文件及允许的网络；资源耗尽防护依赖宿主资源控制，网络策略也要单独配置。它不能代替安全架构。[gVisor：Security Model](https://gvisor.dev/docs/architecture_guide/security/)

项目设计：

- 不可信执行运行在独立工作节点，通过 gVisor 类沙箱或经验证的等效隔离方案执行；具体运行时在原型兼容性及安全验证后锁定。
- 每次构建和测试创建临时环境，限制 CPU、内存、进程数、磁盘写入、输出大小及总时间，超限终止并回收。
- 默认禁止出网及云元数据、内网地址访问；依赖获取由受控镜像与批准清单完成，不授予任意包管理脚本无限联网能力。
- 只挂载所需输入与临时输出目录，不挂载平台源码根目录、宿主 Docker socket、生产配置或共享账户凭据。
- 多人规则通过有限 IPC 协议接收动作、时间与随机源，返回新状态及玩家视图；不直接取得数据库连接、支付 SDK、账号令牌或任意文件访问。
- 每局或隔离租户的资源归属明确，规则崩溃不能拖垮其他游戏或平台业务。中止规则执行后，由平台处理房间通知与清理。

上述方案提供可实施的边界，不构成“绝无逃逸”保证；上线前必须测试实际宿主、运行时版本、策略配置和依赖兼容性。

## 四、PostgreSQL 账本与异步任务

### 4.1 事务和余额并发

资料事实：数据库事务将多步骤合为原子操作；PostgreSQL 的行锁可协调同一行上的并发更新，并在事务结束时释放。[PostgreSQL：Transactions](https://www.postgresql.org/docs/current/tutorial-transactions.html)、[PostgreSQL：Explicit Locking](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS)

项目设计：账号余额、点数批次分配、冻结记录、任务记录和待发送事件在一个数据库事务中提交。用条件更新或明确行锁保证余额检查与扣减一致；不能先在应用内读余额，再无条件写回。

事务内不要等待外部 AI、支付或短信调用。支付通知、任务完成及退款返回都以独立的幂等事务处理，遇到死锁或可重试冲突时使用有界重试。

### 4.2 唯一约束与幂等

资料事实：唯一约束可限制单列或列组合重复；默认情况下含空值的唯一键不一定阻止重复，因此幂等关键字段应明确非空。[PostgreSQL：Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-UNIQUE-CONSTRAINTS)

项目设计：对渠道交易编号、业务入账键、任务结算键以及点赞的用户与游戏组合建立非空唯一约束。请求幂等键需绑定账号、操作类型与请求内容摘要，同一键携带不同请求内容应返回冲突。

唯一键不能单独保证整个工作流正确；状态条件与流水、余额必须共同提交，并限制结算和释放对同一冻结记录互斥。

### 4.3 Outbox 与可选队列

项目设计：在业务事务内写入 outbox 事件，再由投递器发送任务或通知。投递按“可能重复”的模型设计，消费者使用幂等键和状态校验，而不宣称跨数据库和外部服务实现天然的恰好一次执行。

小规模试运营可以先使用数据库作任务事实来源，配合独立工作进程和任务租约。Redis 等队列或缓存可按容量需要引入，但不得成为点数、订单和任务终态的唯一记录。缓存丢失不应造成余额归零或重复收费。

## 五、文件与版本存储

项目设计：原始上传包、可编辑源码、构建产物与审核快照分别保存，数据库记录对象标识、摘要、大小、所属版本和访问级别。

源码及未批准产物保持私有，下载需验证作者归属与导出权限。公开游玩的产物只由对应授权与资源网关提供；对象地址和可预测文件名不是访问控制。

已审核版本不可原地覆盖；发布只改变当前版本引用。生命周期清理需排除正在游玩、审核中、争议保留及回滚保留的对象。对象存储供应商与区域在部署评估时选择，本文不预设其定价或区域可用性。

## 六、实施前验证清单

1. 用恶意 iframe 消息、重新导航、重复端口和超大消息验证桥接鉴权；确保游戏不能获取平台账号凭据。
2. 用无限循环、内存耗尽、文件越界、依赖脚本和出网探测验证构建及规则沙箱，检查超限回收和日志脱敏。
3. 用并发创建、支付重复通知、执行器崩溃和迟到结果验证账本、任务状态与 outbox。
4. 对原有 12 款游戏回归玩法和玩家私有视图；验证从旧规则接口到新隔离协议的适配。
5. 测试下架通知、缓存、重连及版本切换；不把成功隐藏大厅卡片等同于停止平台运行授权。
6. 记录设备、浏览器、部署配置和负载条件后再给出性能结论。本文不提供未经测试的并发承诺或服务器报价。
