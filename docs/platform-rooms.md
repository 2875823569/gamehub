# 官方权威房间与本机容量基线

当前官方 12 款游戏使用 PostgreSQL 保存权威快照，API 进程运行仓库内受信任的 `HostGame`。这不是 UGC 多人沙箱；不可信服务端规则继续关闭，等待独立强隔离执行节点验收。

## 房间边界

创建房间固定数据库中的已发布游戏版本。房间邀请与测试访问资格分别校验，游客身份由当前测试会话绑定。每次读取、动作提交及连接续期重新验证环境世代、测试授权、游戏限制和成员游玩会话。

每房间本实例串行计算候选，提交事务检查数据库 `sequence`、`lease_owner`、`lease_epoch`、租约有效期与成员权限。动作 ID 与请求摘要共同去重。客户端仅收到自己的 `RoomView`，不接收完整权威快照。官方规则 12 款启动、私密骰子投影、重复动作、旧租约拒绝、游戏限制和 API 重启后正在进行的房间恢复均有真实 PostgreSQL 测试。

主持实例租约为 15 秒，成员可在最后活动后 60 秒内恢复；房主离开时转交房主，正在进行的对局按现有玩法规则中止。后台强制限制在下一次状态/动作检查失效。每房间每三秒统一回查所有已连接成员的授权、刷新心跳和玩法超时；本实例动作、开始、加入、退出完成后即时触发对应房间投影推送。共享的是数据库状态刷新，每个玩家仍有独立的授权结果和私密投影。

## HTTP 与 WebSocket

HTTP 路由都在 `/api/v1` 下。修改操作使用测试访问 CSRF，不使用账号或后台 CSRF。

- `POST /rooms`：`{gameId}`，返回 `roomId / inviteToken / sequence / versionId / view`。
- `POST /rooms/:id/join`：`{inviteToken}`。
- `GET /rooms/:id/state`：返回当前成员投影。
- `POST /rooms/:id/start`：`{actionId, expectedSequence}`。
- `POST /rooms/:id/actions`：`{actionId, expectedSequence, action}`，`action` 沿用官方 `ClientAction`。
- `POST /rooms/:id/leave`：退出房间。
- `POST /rooms/:id/connection-tickets`：返回 `{ticket, expiresInSeconds:30, path}`。

客户端连接票据返回的 WebSocket 路径，并在五秒内发送首帧 `{type:"authenticate",ticket}`。平台 Origin 必须在允许列表中；票据 30 秒有效且只能消费一次，不能放进 URL。服务端状态帧为 `{type:"state",data:{roomId,sequence,versionId,view}}`。授权错误帧为 `{type:"error",code,message}`，随后关闭连接。这个通道只读，修改仍走 HTTP。

## 2026-11-10 安静复测

将状态刷新改为每房间共享，并协调其他代理暂停全量测试、构建和备份后，重新执行三档和目标负载。**20 房间、100 玩家、两个模拟任务并行时，默认 10 连接池的动作推送 p95 为 322.09 毫秒；仅将测试池上限调到 20 的对照样本为 290.86 毫秒。后者在这次短时样本中低于 300 毫秒目标，但仍未证明完整容量验收通过。** 最终交付时本机 `.env` 采用已测过的20连接配置；仓库默认与 `.env.example` 仍为10，其他部署需按实际负载和数据库总连接预算验证。

- **10 房间 / 20 人**：50 次动作，推送 p50 / p95 / p99 **146.82 / 165.32 / 171.78 ms**；HTTP 动作响应 p95 108.28 ms；API RSS 峰值 127.99 MiB，池等待峰值 1。测量段 1.83 秒。
- **25 房间 / 50 人**：125 次动作，推送 p50 / p95 / p99 **324.62 / 378.35 / 389.40 ms**；HTTP 动作响应 p95 279.70 ms；API RSS 峰值 151.43 MiB，池等待峰值 18。测量段 2.94 秒。
- **50 房间 / 100 人**：250 次动作，推送 p50 / p95 / p99 **774.22 / 984.80 / 1093.21 ms**；HTTP 动作响应 p95 693.32 ms；API RSS 峰值 186.53 MiB，池等待峰值 42。测量段 5.62 秒。
- **20 房间 / 每房 5 人 / 两个模拟任务并行**：100 次动作，推送 p50 / p95 / p99 **270.08 / 322.09 / 332.99 ms**；HTTP 动作响应 p95 228.38 ms；API RSS 峰值 152.48 MiB，池等待峰值 14。测量段 2.62 秒。
- **相同目标场景 / 池上限 20 对照**：100 次动作，推送 p50 / p95 / p99 **252.80 / 290.86 / 327.56 ms**；HTTP 动作响应 p95 222.43 ms；API RSS 峰值 152.54 MiB，实际连接峰值 20，池等待峰值 1。测量段 2.53 秒，8 项模拟任务全部成功，并发峰值 2，重叠约 2.33 秒。排队减少与延迟降低支持进一步检查连接池和锁等待，但不能证明增加连接数是唯一原因或适用于所有负载。

这五档动作、HTTP、WebSocket 错误数全部为 0。10 连接池目标档两个模拟执行循环共领取并成功完成 8 项任务，同时处于运行状态的任务峰值为 2，重叠运行约 2.19 秒。它们运行真实领取/租约/静态产物/结算/通知逻辑，每项额外模拟 500 毫秒提供方等待；执行循环在负载生成器进程中，未调用真实 AI，也不代表模型计算负载。数据库为 PostgreSQL 18.6。两个目标档游戏快照平均约 1414—1451 字节，属于非常小的状态。

原始 JSON 使用 `quiet-shared-room`、`quiet-target-with-mock-workers` 和 `quiet-target-pool20` 标签区分这五档，`databasePoolMax` 记录每档配置；旧结果保留为 `overlapped-api-tests-and-build`。旧读路径与共享读路径之间代码和并行负载都发生变化，不能用作单变量优化收益证明。所有临时 `capacity_<uuid>` schema 已清理，模拟产物的专属临时目录也已清理。

## 初测记录：旧读路径与并行任务干扰

结论：短时突发测量中，10 个双人房间的动作到另一位玩家收到 WebSocket 投影的 p95 约 269 毫秒；25 和 50 房间分别约 616 毫秒和 3715 毫秒。后两档超过方案中的 300 毫秒目标。本次不能证明文档 13 的完整容量门槛达标。

环境为 Windows 10 `10.0.19045`、Node `v24.21.0`、Intel Core i5-8400 2.80GHz、6 个逻辑 CPU、约 31.9 GiB 内存。HTTP、WebSocket 和 PostgreSQL 都在 localhost。API 使用单独 Node 子进程，客户端负载生成器是另一个进程，API PostgreSQL 池最大连接数保持现有配置 10。**上述第一组三档测量与主任务的全量 API 测试和前端构建重叠，不是机器空闲基线。** 它使用优化前每位玩家每秒独立刷新状态的实现，不能将结果变化全部归因于后续代码优化。

使用官方“数字炸弹”，每房间两位真实 WebSocket 客户端，各房间在同一批次并发发动作，每房间五次，批次之间至少间隔 200 毫秒。通常提交公开合法范围的下界猜数；若对局结束则由房主重新开局。计时从发起 HTTP 动作之前，到另一位玩家首次收到该次提交序号对应的 WebSocket 投影。没有用 HTTP 响应时间替代推送延迟。

- **10 房间 / 20 人**：50 次动作成功，推送 p50 / p95 / p99 为 **150.66 / 268.71 / 289.93 ms**。API RSS 峰值 127.69 MiB，数据库池等待峰值 0，事件循环 p95 16.15 ms。
- **25 房间 / 50 人**：125 次动作成功，推送 p50 / p95 / p99 为 **369.50 / 616.41 / 711.56 ms**。API RSS 峰值 158.02 MiB，数据库池等待峰值 17，事件循环 p95 15.77 ms。
- **50 房间 / 100 人**：250 次动作成功，推送 p50 / p95 / p99 为 **2814.89 / 3714.96 / 3948.82 ms**。API RSS 峰值 154.84 MiB，数据库池等待峰值 91，事件循环 p95 14.94 ms。测量段约 18.06 秒，包含建库、准备和清理的整个阶段约 56.15 秒。

三档记录的动作失败率、HTTP 错误数和 WebSocket 错误数均为 0。50 房间档 HTTP 动作响应 p95 为 3018.40 ms，PostgreSQL 采样发现活动连接峰值 10、等待锁连接峰值 9。连接池排队与延迟上升同时出现，但本次没有完成锁热点和磁盘等待的因果诊断，不能据此断言只需增加连接数。

原始结果追加保存到 `work/platform/capacity.json`，包括时间、设备、采样数量、分位数、错误详情、API CPU/内存/事件循环/连接池指标，以及数据库活动和落库计数。数据库活动采样覆盖 API 与准备数据的连接池；准备池在测量阶段空闲，因此“空闲连接数”可能超过 API 的 10 个连接。CPU 百分比以占满一个逻辑核心为 100%，不是整机 CPU 百分比。测试工作目录被 Git 忽略，需要共享原始证据时单独保留该 JSON。

## 复现与安全范围

仓库根目录执行；需要已经启动本机 PostgreSQL 和安装项目依赖：

```powershell
node --import tsx scripts/platform-capacity.mjs --rooms 10 --rounds 5
node --import tsx scripts/platform-capacity.mjs --rooms 25 --rounds 5
node --import tsx scripts/platform-capacity.mjs --rooms 50 --rounds 5
node --import tsx scripts/platform-capacity.mjs --rooms 20 --players 5 --mock-workers 2 --rounds 5 --label quiet-target-with-mock-workers
node --import tsx scripts/platform-capacity.mjs --rooms 20 --players 5 --mock-workers 2 --rounds 5 --pool-max 20 --label quiet-target-pool20
```

也可使用 `--rooms 10,25,50` 顺序执行。脚本只接受 10、20、25、50 房间，每房 2—5 人且总数不超过 100，以及每房 1—5 次动作；模拟 worker 数量为 0 或 2；`--pool-max` 默认 10、允许 1—30，仅影响临时测量进程配置。档位失败或动作失败率超过 10% 时停止后续档位。测量段超过 45 秒时停止后续动作批次，不会自动扩大到 500 客户端。各档使用随机 `capacity_<uuid>` schema，创建全套迁移，完成后校验名称并仅删除该 schema，不修改 `public` 或开发业务数据。数据库地址来自 `GAMEHUB_TEST_DATABASE_URL`，未设置时使用本机开发数据库；明确拒绝非本机 PostgreSQL 地址。该数据库仍承受测试负载，勿把共享生产数据库映射到本机端口运行本脚本。

为了聚焦房间负载，测试访问会话通过受信任 `AccessStore` 准备，房间创建、加入、开始、连接票据和动作全部经过实际 HTTP/Origin/CSRF。此测量不代表短信、邀请兑换速率或浏览器渲染容量。

## 仍需补充的容量与扩展工作

本次是小状态官方规则的短时阶梯突发基线，未覆盖持续稳定负载、慢客户端、广域网、TLS、浏览器/iframe 渲染、UGC 规则复杂度、真实 AI 负载、系统化限流策略和共享宿主机干扰。因此即使某一档 p95 低于目标，也不能替代文档 13/24 的完整验收。

当前只有本实例订阅者会得到即时广播；跨实例没有消息总线、房间主持路由和无缝转发。请求到达其他仍有效的租约实例会返回 503，待租约失效可安全接管，但这不是透明横向扩展。现在应使用单 API 实例，或由部署提供房间一致的主持路由；普通按连接粘性的负载均衡不足以保证两个玩家进入同一个主持实例。后续应先定位数据库锁与池排队热点、降低重复授权和轮询事务成本，在保留撤权与租约保证的前提下复测，再设计跨实例通知和主持路由。
